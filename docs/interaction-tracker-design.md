# 设计文档：点赞与投币记录（interactions）

> 状态：设计已定稿，接口语义已完成**匿名实测**；登录态下的分页与保留窗口仍需用
> [verify/phase5-interaction-api-probe.js](../verify/phase5-interaction-api-probe.js) 在你的账号上确认。
> 相关文档：[following-tracker-design.md](./following-tracker-design.md)、
> [content-preservation-design.md](./content-preservation-design.md)

## 需求

1. 记录自己**点赞过的视频**与**投币过的视频**，永久保存在本地。
2. B 站只保留很短一段时间的这两个列表，且**删掉之后用户无从追溯**——这正是本功能存在的理由。
3. 列表里消失的条目**绝不能直接删除**：可能是你取消了，也可能是 B 站自己不再保留。
4. 消失的条目要尽力判定原因（取消 / 稿件被删 / 稿件不可见），判定不了也必须留档。
5. 提供独立页面浏览、搜索、筛选，并纳入 WebDAV / 本地目录 / JSON 三套备份。

## 现状核对

- 仓库原有的 `likedMusic` store 是上游「听歌」功能的产物（`bvid` + `added_at`），
  页面已删除、数据保留，**与本功能的"点赞过的视频"完全无关**，不要复用。
- 仓库已有完整的"消失留档"范式（`vanishedFavResources` + `utils/favVanishedDiff.ts`）
  与"图片字节归档"范式（`assets` + `utils/favCoverArchive.ts` 的泛型 `runCoverArchive`），
  两者都能直接复用。
- 仓库已有纯函数 + 注入依赖的同步编排范式（`utils/followingSync.ts`），本功能沿用。

## 接口实测（匿名可复现的部分）

以下结论全部由 `https://api.bilibili.com/x/space/...` 直接请求得出，**不需要登录**（对公开了隐私设置的用户）。

### 0. 数据来源就是个人主页的两个模块

B 站个人空间（`space.bilibili.com/{mid}`）上的「最近点赞的视频」「最近投币的视频」两个模块，
前端调的就是下面这两个接口。本功能抓的正是它们——**主页能看到的，我们就能记住；主页没有的，我们也变不出来。**

翻页参数已经穷举验证过，全部无效（同一 mid 下返回的首尾条目完全一致）：

| 试过的写法 | 结果 |
| --- | --- |
| 基线 `?vmid=` | 20 条 |
| `&pn=2` | 同样的 20 条 |
| `&ps=100&pn=1` | 同样的 20 条 |
| `&ps=5` | 同样的 20 条 |
| `&page=2` | 同样的 20 条 |
| `&offset=20` | 同样的 20 条 |
| `&pagination_str={"offset":""}` | 同样的 20 条 |

因此抓取层照发分页参数（万一 B 站放开就自动多抓几页），但**不指望**能翻页；
判定层也从不假设"没抓到 = 不存在"。

### 1. 点赞列表

```
GET https://api.bilibili.com/x/space/like/video?vmid={mid}
Cookie: SESSDATA=...
```

- 响应：`data.list`，元素是**完整的稿件详情对象**（`aid/bvid/title/pic/pubdate/ctime/duration/owner{mid,name,face}/stat`）。
- **实测固定返回 20 条**。`pn` / `ps` / `p` 三种分页参数全部被忽略：
  同一 mid 下 `?ps=5`、`?pn=2&ps=5`、`?p=2` 返回的 20 条**完全一致**（首条 aid 相同）。
- **接口不返回"点赞时间"**。`ctime` 是稿件创建时间（实测与 `pubdate` 相同），不是点赞时间。
  因此本功能只能把**首次观测到它的时间**当作点赞时间的近似值，并在界面上如实标注。
- 隐私未公开时 `code = 53013`；`vmid` 不存在时为 `-400`。

### 2. 投币列表

```
GET https://api.bilibili.com/x/space/coin/video?vmid={mid}
Cookie: SESSDATA=...
```

- 响应：`data` **直接是数组**（不是 `{list}`），字段与上者基本一致，另有：
  - `coins`：你给这条稿件投的币数
  - `time`：**真实的投币时间**（秒级时间戳）——这是三个接口里唯一给得出互动时间的
- 同样实测最多 20 条，同样忽略分页参数。

### 3. 保留窗口

- 空间设置接口 `space.bilibili.com/ajax/settings/getSettings` 里两个板块的字面名称就是
  **「最近点赞的视频」**（`privacy.likes_video`）与 **「最近投币的视频」**（`privacy.coins_video`）——
  官方措辞本身就说明这是"最近 N 条"的窗口，不是全量历史。
- `x/web-interface/archive/has/like` 的社区文档明确写着：它**只能判断近期是否点赞**，
  半年前点赞的视频再查已经是 0。也就是说 B 站侧的互动记录本身就会过期。
- 结论：**这两个列表是滚动窗口，条目会自己掉出去**。掉出去 ≠ 你取消了。
  界面与文档都不能承诺"B 站上还能查到"，只能承诺"我们本地替你记住了"。

### 4. 判定用的探测接口（需要登录）

| 接口 | 用途 | 匿名结果 |
| --- | --- | --- |
| `x/web-interface/view?bvid=` | 稿件是否还在（`0` / `-404` / `62002`） | 可用，不需要登录 |
| `x/web-interface/archive/relation?bvid=` | `data.like`（是否点赞）/ `data.coin`（你投的币数） | `-101` 账号未登录 |
| `x/web-interface/archive/has/like?bvid=` | 是否点赞（只有 0/1） | `-101` 账号未登录 |

`relation` 一个请求就能同时回答"点赞还在不在"和"投币还在不在"，因此消失判定统一用它，
`has/like` 只作为 `relation` 不可用时的兜底。

## 对照参考项目：LifeArchiveProject/BilibiliHistoryFetcher

本项目 `routers/interaction_records.py` 做了同一件事（收藏 + 点赞 + 投币的互动记录留存），
结论与本设计**完全吻合**，可以直接当作独立复核：

- 它抓点赞/投币用的就是本文这两个接口，且**只传 `vmid` 一个参数、完全不翻页**
  （`fetch_space_interactions` → `params={"vmid": up_mid}`）。
- 它的 `/api-capabilities` 自述：

  | source | time_field | scope | confidence |
  | --- | --- | --- | --- |
  | favorite | `fav_time` | created favorite folders, paginated | high |
  | like | **None** | space **recent** liked videos | medium |
  | coin | `time` | space **recent** coined videos | medium |

  并明确写道：投币接口带 `time`，但它**"仍然只是一个 recent space list，而不是经过验证的全量历史归档"**；
  点赞接口**"不提供稳定的点赞时间戳"**。
- 它的 README 进一步写明："**点赞 Web 接口主要是最近点赞视频列表，当前未发现可靠的全量历史分页和点赞时间字段**"，
  且用户信息接口的注册时间字段通常返回 `0`，因此**无法以账号注册时间作为全量起点**。
- 它把没有可靠动作时间的记录记为 `action_time_source = "unavailable"`，统计时单独暴露
  `time_quality`（"有 N 条互动记录缺少可靠动作时间"）。

**结论（与用户反馈一致）：历史记录无法找回，这个功能只能从安装那天开始记。**
本设计没有假装能做到更多：界面上一律标注"首次记录时间 / 近似"，
并把"只有近似时间的条数"直接显示出来（对应它的 `time_quality`）。

### 与它刻意不同的三处取舍

| 点 | 参考项目 | 本项目 | 理由 |
| --- | --- | --- | --- |
| 窗口内的先后顺序 | 点赞回退用 `pubtime/ctime/fetch_time` 作为 `effective_time` | 记 `listRank`（接口返回的原始名次），排序时作为第二判据 | 列表本身按点赞时间倒序，名次是**真实**的相对先后；用稿件发布时间排序反而会给出错误的时间关系 |
| "消失"的处理 | 直接 upsert，不区分条目为何不在列表里 | 二次探测（`view` + `relation`）后标注 `retained`/`ended`/`content_deleted`/`content_hidden`，探测失败停在 `unlisted` | 掉出 20 条窗口 ≠ 你取消了；这正是本仓库在收藏夹上已经确立的"先留档、再判定、绝不硬删"原则 |
| 收藏 | 并入同一张互动表，用 `source` 区分 | **不并入**，继续用既有的 `favResources` + `vanishedFavResources` | 收藏已经有完整的消失档案、恢复流水线与封面归档；再存一份会产生两个真相源 |
| 原始 JSON | 每条存 `raw_json` | 不存；改为存 `firstTitle` 并归档封面字节 | 原始 JSON 会成倍放大存储，而真正需要留住的"消失前长什么样"由首次标题与图片字节覆盖得更彻底 |

它另外做了两件本项目暂未做的事，可作为后续可选方向：把互动记录**回填进观看历史**标为"互动补充"，
以及把互动数据接进年度总结分析。

## 设计

### 1. 状态模型

消失判定必须区分五件不同的事，**一个布尔值不够用**，因此用单枚举：

```ts
type InteractionState =
  | "listed"          // 最近一次同步仍在 B 站列表里
  | "unlisted"        // 已不在列表，尚未判定（探测未做 / 探测失败）
  | "retained"        // 已不在列表，但探测证明互动仍在（B 站只是不再展示）
  | "ended"           // 已不在列表，内容仍在，但探测显示互动已不存在
  | "content_deleted" // 稿件不存在
  | "content_hidden"; // 稿件不可见（转私密 / 被限制）
```

**关于 `ended` 的诚实边界**：探测到 `like=false` / `coin=0` 时，
「你取消了」与「B 站自己不再保留这条记录」在接口上**无法区分**。
界面文案必须写成"互动已结束"，并在说明里点明这层歧义，不能promise成"你取消了点赞"。

**关于 `retained` 的价值**：它是唯一一条"B 站列表藏起来了、但互动其实还在"的证据，
也是本功能最独有的信息。它靠 `relation` 的 `like=true` / `coin>0` 直接得到，不靠猜测。

### 2. 数据模型

#### 2.1 `interactions`（keyPath `id`，索引 `type` / `bvid` / `state` / `observed_at` / `[type, observed_at]`）

主键用字符串 `\`${type}:\${bvid}\``：同一条视频既可能被点赞也可能被投币，
两者必须是两条互不覆盖的记录。复合主键 `[type, bvid]` 也能表达，
但字符串主键在备份合并、按 id 打补丁、跨 store 判重时都更直接。

| 字段 | 说明 |
| --- | --- |
| `id` | `\`${type}:\${bvid}\`` |
| `type` | `"like" \| "coin"` |
| `bvid` / `aid` | 稿件标识 |
| `title` | **最新一次已知的真实标题**，永不写入"已失效视频"这类占位文案 |
| `firstTitle` | **首次观测到的标题，只写一次、之后永不覆盖**——回答"我当时点的赞是哪条视频" |
| `cover` / `coverAssetId` | 当前封面 URL / 指向 `assets` 的封面字节归档 |
| `duration` / `pubdate` | 时长（秒）/ 稿件发布时间（秒） |
| `authorName` / `authorMid` | UP 主（接口自带 `owner`，不需要额外请求） |
| `interactedAt` | 互动时间（毫秒）。投币取接口的 `time`；点赞只能用首次观测时间 |
| `interactedAtExact` | `interactedAt` 是接口给的真实时间（true）还是首次观测的近似值（false） |
| `listRank` | 最近一次在线列表中的位置（0 起，越小越新） |
| `coins` | 仅投币：投币枚数 |
| `state` | 上面的单枚举 |
| `firstSeenAt` / `lastSeenAt` / `lastSeenOnlineAt` | 首次入库 / 最后一次被同步扫到 / 最后一次在线可见 |
| `unlistedDetectedAt` / `endedDetectedAt` | 首次判定"不在列表" / "互动已结束"的时间 |
| `probeAttemptedAt` / `probeError` | 探测时间与失败原因 |

#### 2.2 不新增事件表

关注模块之所以有 `followingEvents`，是因为它的核心价值是**关系变化的时间线**。
点赞/投币的核心价值是**记录集合本身**：每条记录的 `firstSeenAt` / `unlistedDetectedAt` /
`endedDetectedAt` 已经把时间点写在自己身上，记录本身就能表达"什么时候入库、什么时候消失"。

> 中途试过再派生一份 `buildInteractionTimeline` 放到总览页的「最近变动」列表里，
> 评审时被否掉了（总览页塞明细太杂），**已连同那个列表一起删除**。
> 需要时间线时按上面三个字段排序即可，不必再引入一层派生。

### 3. 判定规则

一轮同步对每种类型（like / coin）分别执行：

1. **抓取**：`pn=1` 开始翻页，每页之间间隔 `pageDelayMs`。
   - 空页 → 结束，`scanCompleted = true`
   - 本页**没有任何新 bvid**（说明接口忽略了 `pn`，第二页仍是同一批）→ 结束，`scanCompleted = true`
   - 本页数量 < `pageSize` → 结束，`scanCompleted = true`
   - 达到页数上限 → 结束，`scanCompleted = false`
   - 任何请求错误 → `scanCompleted = false`
2. **写快照**：在线列表里出现的条目
   - 新条目 → 建档，`state = "listed"`，`firstSeenAt = now`
   - 已有条目 → 刷新标题/封面/UP 主/排名，`state` 回到 `"listed"`，`lastSeenOnlineAt = now`
   - **标题与封面只在"新值不是占位内容"时才覆盖**，占位内容一律保留旧值
3. **消失判定**：本地有、本轮在线列表里没有的条目
   - **`scanCompleted === false` 时一律不判定**（网络抖动或翻页被截断时，缺的可能只是没抓到）
   - 判定成立 → `unlistedDetectedAt ??= now`，进入探测队列
   - 已在 7 天内探测过的条目不再探测，直接沿用已有 `state`
4. **探测**（每轮最多 `maxProbesPerRun` 条，按 `lastSeenOnlineAt` 从新到旧排序）：
   - 先 `x/web-interface/view`：`-404` → `content_deleted`；`62002` → `content_hidden`
   - 稿件还在 → 再 `x/web-interface/archive/relation`：
     - `like === true`（点赞）/ `coin > 0`（投币）→ `retained`
     - 否则 → `ended`
   - 任何一步失败 → `state` 保持/置为 `"unlisted"`，记 `probeError`，7 天后重试
5. **落库**：快照与判定结果一个事务写入。

### 4. 为什么"滚动窗口"不再需要额外的完整性护栏

关注模块必须靠"是否扫完全部 total 条"来防止误判取关，因为那里**没有**任何事后核实手段。
本功能有 `relation` 这个**权威探测**：条目为什么不在列表里，直接问接口就行。
所以护栏从"不许判定"改成"判定必须经过探测"，探测失败就停在 `unlisted`，绝不猜。
真正需要护栏的是**请求预算**：掉出窗口的条目会随使用时间线性增长，
因此每轮探测有条数上限，剩下的下一轮继续，不会一次性打出几千个请求。

### 4.1 主页访问时顺手补抓

20 条窗口意味着"两次同步之间的点赞多了，早的就永久丢失"。所以除了定时任务，
后台还监听 `tabs.onUpdated`：只要浏览器完成了对 `space.bilibili.com/*` 的导航，
就**补抓一次**（不判定）。两条自我约束：

- 最小间隔 30 分钟（`DEFAULT_INTERACTIONS_PAGE_TRIGGER_GAP_MINUTES`），连点页面不会连发请求；
- `maxProbesPerRun: 0`，即**只抓不探测**——浏览是浏览，消失判定留给定时任务；
  且这类补充同步不更新 `INTERACTIONS_LAST_SYNC` 水位，否则频繁逛主页会把定时任务一直往后推。

用 `tabs.onUpdated` 而不是改 content script：后台本来就有 `tabs` 权限，不必多动一个注入脚本。
抓的始终是**自己**账号的列表，因此访问谁的主页都无所谓。

评审过程中被推翻的两个方案一并记在这里，免得以后再绕回去：

| 试过的方案 | 为什么放弃 |
| --- | --- |
| 「全部」页按视频合并点赞+投币成一张卡 | 合并本身不解决根本问题：同一条视频仍然要在卡上说两件事。**最终改为不设「全部」页，点赞 / 投币各自一个 tab** —— 类型由 tab 决定，卡片上一律不写类型文字，也不再出现"两张几乎一样的卡" |
| 卡片上放「♥ 点赞 / ◎ 投币」图标徽章 + 完整时间 | 图标与徽章本身成了视觉噪音；"♥ 点赞 · ≈2026/10/13 23:13"这种句子既长又重复。**最终改为去图标、去类型文字**，只留必要的一格日期 |

最终形态：

- 路由 `/interactions`，主区顶部是**类型 tab（点赞 / 投币）**，不带「全部」页。
- 侧栏只留**状态筛选三档**（全部 / 仍在列表 / 已不在列表）+ 同步信息。
  内部状态机有六个取值，但界面不照搬——B 站只给 20 条，大部分记录永远停在「仍在列表」，
  把六个状态平铺出来就是一屏的 0。一条数据都没有时干脆不铺筛选行，只提示"去同步"。
  状态计数按当前 tab 实时算，与筛出来的结果永远一致。
- 主区：搜索（标题、原名、UP 主）、排序、四列网格（`grid-cols-2 md:grid-cols-3 xl:grid-cols-4`）、分页。
  不用 auto-fill：那样在超宽屏会一路塞到 5～6 列，卡片窄到标题频繁折行。
- **一张卡 = 一条互动记录**（数据层点赞与投币本来就是两条独立记录，展示层也不再合并）。
  卡片内容：封面（优先本地归档字节）+ 时长、标题、原名（若改过名）、
  仅在异常时出现的状态 chip、页脚 **左作者 / 右日期**（与仓库其它页面同一套排版）。
- **时间只给可信的那种**：
  - 投币接口给真实时间 → 页脚右下角显示**完整日期**（`2026/10/10`，与收藏页同一套写法）；
    "3 天前"这类相对说法只出现在 hover 里。
  - **不显示投了几枚**：用户要的是"记录下我投过币"，`×2` 前缀与"两枚叠在一起"的硬币图标都只是噪音。
    枚数仍然照常写进数据与备份（`InteractionItem.coins`），只是不展示。
    封面上的类型图标一律照 B 站自己的设计，且**不带底色**（三版才定下来）：
    **点赞 = 描边大拇指**（B 站点赞图标就是大拇指，心形在 B 站是"喜欢/收藏"的语义），
    **投币 = 描边圆 + 「币」字**（B 站投币按钮与"1 硬币 / 2 硬币"提示都是"圆里一个币字"）。
    图标直接贴在封面上，靠一层 drop-shadow 保证亮/暗封面都看得清。
    被否掉的两版：色块角标（太重、喧宾夺主）、白圆挖币字（同样是一块底色）。
    lucide 的 `Coins`（两枚叠着的硬币）已弃用：既不忠于 B 站设计，也容易被读成"投了两枚"。
  - 点赞接口不返回点赞时间 → **卡片上不显示日期**。首轮同步就在列表里的记录只能说"早于开始记录"，
    逐张写「早期」会重演一片重复，因此一律不写，解释放进整张卡的悬停说明。
    这条解决的是第一版最刺眼的问题：首轮 20 条记录的"点赞时间"全都是同一次同步的时刻。
- **BV 号不在卡片上显示**（评审认为不实用）：只在悬停卡片时出现一个小小的复制图标，
  点击即复制并弹出提示；日常浏览时它不占版面。
  - **「仍在列表」不显示任何徽章**：它是默认态，每张卡都挂绿标等于给扫读加噪音。
  - **不显示"首次记录时间"**：它只有两个用途，都已被别的元素接管——
    点赞没有真实时间时充当时间（并进点赞那一行，前面加 `≈`），以及算"哪天起不在列表"
    （只在真消失时以 chip 旁边的小字出现）。独立成行只会让人问"这是干嘛的"。
  - `≈` 的含义（B 站不返回点赞时间）在页面顶部统一解释一次，不逐条啰嗦。
  - 标题与首次记录不同时显示「原名 xxx」——说明这条稿件后来改过名。
- 顶部固定说明：**"B 站只保留最近 20 条，本页是你的本地永久副本"**——
  不写这句话，用户不会知道这个页面的价值在哪。

### 6. 备份

`interactions` 作为独立备份项加入 WebDAV / 本地目录 / JSON 三套备份与导入预览。
合并策略：按 `id` 取并集，冲突时保留 `lastSeenAt` 更大者（观测更晚的更准），
`firstTitle` 与 `firstSeenAt` 取**更早**的一方（首次观测才是真相）。
封面字节照旧**不进任何备份**（`assets` 是纯缓存，本地目录备份会单独写成 `images/`）。
