# 设计文档：收藏夹内容保全（消失语义改造 + 视频封面归档）

> 状态：设计已评审通过，尚未实现。
> 相关文档：[following-tracker-design.md](./following-tracker-design.md)（关注追踪与数据面板）

## 背景与目的

本项目的根本目的是**记录并备份数据，防止因外部原因导致内容丢失**。已确认的丢失场景之一是：UP 主删除视频、视频被下架或转为私密后，本地收藏记录连同"曾经存在过什么"的证据一起消失。

本模块负责让**内容层**（收藏夹里的视频）的消失可追溯，并保住视频封面的图像。

> 关注模块只保存 UP 主基础信息、不保存投稿内容，因此"丢了什么内容"的答案完全依赖本模块与既有历史记录模块。

## 现状核实（关键，含代码位置）

### 1. 全量同步会硬删除本地记录

[entrypoints/background.ts](../entrypoints/background.ts) 的 `syncFavoriteFolderResources` 收尾逻辑：

```ts
if (isFullSync) {
  if (!allPagesFetched) {
    throw new Error(`收藏夹「${folder.title}」未完整同步，已跳过本地清理`);
  }
  const idsToDelete = localResources
    .filter((item) => !onlineResourceIds.has(item.id))
    .map((item) => item.id);

  if (idsToDelete.length > 0) {
    await deleteFavResources(folder.id, idsToDelete);
  }
}
```

**问题**：这段逻辑无法区分两种完全不同的原因：

1. **你主动取消了收藏** → 删除本地记录是合理的
2. **视频被 UP 主删除 / 下架 / 转私密** → 删除本地记录等于销毁证据

而 B站 收藏夹接口**不返回"这条为什么消失"**。这是接口能力限制，不是实现缺陷——因此不能靠更聪明的判断解决，只能靠保守留档。

### 2. 不是所有删除都会丢（Phase 1 实测：L1 是主路径）

[utils/db.ts](../utils/db.ts) 的 `saveFavResources` 有一段"失效保护"：若在线返回的标题是 `已失效视频`，会保留本地旧的 `title` / `cover` / `intro` / `upper` / `ctime`。

**实测结果（自身账号，扫描 3 个收藏夹共 334 条）**：

- 已失效条目 **39 条，占 11.7%**，说明"失效占位"是真实且常见的路径，条目**不会**从收藏夹消失。
- `attr` 取值分布 `{0: 295, 1: 14, 9: 24, 25: 1}`——**14+24+1 = 39 恰好等于失效条目数**，即 `attr !== 0` 与 `title === "已失效视频"` 在本样本中完全一致。
- 39 条失效条目**全部保留 `bvid`、`cover` 以及完整的 UP 主 `mid/name/face`**。

因此四种走向：

| 情况 | 结果 |
| --- | --- |
| 视频变成 `已失效视频` 占位留在收藏夹（**主路径，实测 11.7%**） | 元数据保住（现有行为） |
| 视频从收藏夹列表彻底消失（边缘情况） | **本地记录被全量同步删除** |
| 你主动取消收藏 | 本地记录被删除 |
| 失效条目仍保留 UP 主真实名字 | 可用于反查已注销 / 改名 UP 主的旧名 |

**判定信号应改用 `attr !== 0` 作为主判定、`title` 作兜底**：现有代码只查 `title === "已失效视频"`，本样本中两者恰好一致所以未暴露问题，但 `attr` 是更本质的信号——一旦 B站 调整 title 文案，现有保护会失效并让元数据被覆盖。

**`attr` 取值的语义**（交叉验证：Phase 1b 实测的 API 返回码 + 社区脚本 `bilibili-favorites-fix` 的标注）：

| `attr` | 含义（社区脚本标注） | Phase 1b 实测 `x/web-interface/view` 返回 |
| --- | --- | --- |
| `0` | 未失效 | `code 0`，正常 |
| `1` | 其他原因删除 / 退回 | `-404 啥都木有`（稿件彻底不存在） |
| `9` | **UP 主自己删除** | `62002 稿件不可见`（B 站仍保留稿件记录） |
| `16` / `25` | 意义未明 | 未采样到 |

两条独立证据对得上：`attr 1` 与 `attr 9` 在 B 站 侧确实是两种不同状态，而不仅仅是一个布尔"失效"标记。这给"消失档案"的 `vanishReason` 提供了更细的分层依据：`attr 9` 暗示内容可能仍有找回途径，`attr 1` 则基本无望。

> 注：该语义来自社区脚本的标注，未经官方文档确认，且 `16` / `25` 仍未知。实现时仍以实测为准。

### 3. 只有全量同步会删

增量同步不删除；且有 `allPagesFetched` 护栏，未完整翻页会抛错并跳过清理。风险集中在用户点击"全量同步"或"一键全量同步全部文件夹"时。

### 4. 图片只有 URL，没有字节（且失效后会被替换为占位图）

仓库没有 blob/资源 store。`FavoriteResource.cover` 与 `FavoriteResource.upper.face` 都是 hdslb CDN 的 URL。

**Phase 1b 实测——情况比"URL 失效"更严重**：

- **失效视频的封面被统一替换为同一张占位图**：6 个采样全部指向 `/bfs/archive/be27fd62c99036dce67efface486fb0a88ffed06.jpg`，尺寸 351×219；而正常条目封面各自不同且尺寸大得多（1077×608、1586×892）。
- **已注销账号的头像被替换为 `member/noface.jpg`**：15 个账号路径去重数 = 1，尺寸 180×180。
- 结论：URL **并未失效，而是被换成了占位图**。所以"等发现消失再去抓"必然只能抓到占位图——**归档的唯一有效形态是在内容还正常时增量抓取**，且越早开始越好。

## 设计

### 1. 分层判定（替换现有硬删除）

保留 `allPagesFetched` 护栏，将其后的清理改为分层处理：

| 层级 | 触发条件 | 处理 |
| --- | --- | --- |
| L1 在线失效 | 在线返回 `attr !== 0`（主判定）或标题为 `已失效视频`（兜底） | 保留旧元数据（**现有行为不变**），补记 `invalidatedAt` |
| L2 在线消失 | 完整翻页后本轮未出现 | 先进入二次探测分类，再写入 `vanishedFavResources` 档案，最后从 `favResources` 移除 |
| L3 增量同步 | 任何情况 | 不删、不标记（**现有行为不变**） |

### 2. 二次探测尽力分类（Phase 1b 实测：可行且更细）

对**本轮新增的** L2 候选（不是全部历史消失项）逐个调用视频详情接口：

- 候选接口：`https://api.bilibili.com/x/web-interface/view?bvid={bvid}`
- **实测无需 WBI 签名**，`aid` 与 `bvid` 两种参数结果完全一致（3/3 对照）
- 返回码语义（实测）：

| 返回 | 含义 | 判定 |
| --- | --- | --- |
| `code 0`、`state 0` | 视频仍在 | `unfavorited`（用户取消收藏） |
| `code -404`、`message "啥都木有"` | 稿件不存在 | `content_deleted`（彻底删除） |
| `code 62002`、`message "稿件不可见"` | 稿件存在但不可见 | `content_hidden`（转私密 / 被限制） |
| 网络失败 / `-352` 风控 / 其他 | 无法判断 | `unknown`（**一律留档**） |

- 实测还发现 `attr` 与返回码有对应关系：`attr 1` → `-404`、`attr 9` → `62002`（样本内 100% 对应）。
- 因此 `vanishReason` 从原设计的两分细化为四分：`unfavorited` / `content_deleted` / `content_hidden` / `unknown`。
- **注意作用范围**：L1（仍在收藏夹的失效条目）**不需要探测**——`attr` 已经给出信号；探测只用于 L2（从收藏夹消失的条目）。

成本：只探测增量项，通常个位数请求。请求间隔与 `-352` 冷却照旧。

### 3. 消失档案 `vanishedFavResources`

```
keyPath: ["folder_id", "id"]
索引: by-vanished-at, by-upper-mid, by-reason
```

字段在 `FavoriteResource` 全部字段基础上增加：

| 字段 | 说明 |
| --- | --- |
| `vanishedAt` | 判定消失的时间 |
| `vanishReason` | `unfavorited` / `content_deleted` / `content_hidden` / `unknown` |
| `probeAttemptedAt` | 二次探测时间 |
| `probeError` | 探测失败原因 |
| `lastKnownTitle` / `lastKnownCover` | 消失前最后已知元数据（冗余保存，防止上游字段被后续覆盖） |
| `coverAssetId` | 指向 `assets` store 的封面字节归档 |

**档案只增不删**，除非用户主动清理。

### 4. 必须接受的取舍

**你主动取消收藏的记录也会一并留档。** 因为接口不返回消失原因，保守做法只能"宁可多留"。二次探测能降低误留比例，但探测失败时仍会留档。

已确认接受此取舍。若不留档，代价是"被删视频的记录也一起丢"——二选一，没有第三条路。

### 5. 收藏夹页语义不变

档案是**独立的 store**，`favResources` 仍按现有逻辑移除，因此：

- `pages/Favorites.tsx` 的列表、搜索、分页、统计**完全不变**
- `AllFavoriteFoldersSyncModal` / `FavoriteFolderSyncModal` 的进度与计数**完全不变**
- 新增一个"消失档案"查看入口（放在数据面板或收藏夹页的独立入口），列出消失项、消失时间、消失原因、消失前标题与封面

这是相对"软消失方案（标记 `vanishedAt` 保留在收藏夹列表里）"的刻意选择：后者会改变收藏夹页的计数与搜索语义（"共 1234 条"含不含消失项？用户取消了收藏却还在列表里），直接制造困惑。

### 6. WebDAV 防复活

消失档案必须参与 WebDAV 双向同步，否则远端旧数据会把已消失的记录"复活"回 `favResources`。仓库已有同类机制可照搬思路：

- `historyTombstones`（事件级/内容级删除墓碑）
- `DELETED_HISTORY_IDS`（阻止远端旧数据复活）

### 7. 视频封面字节归档

**必须在封面 URL 还正常的时候抓取。** 实测已确认：视频失效后封面会被**替换为统一占位图**（见现状核实第 4 节），所以等发现消失时再抓，只能抓到占位图。因此归档是**持续任务**：

- **一次性回填**：对现有正常条目批量抓取封面。实测规模参考：6 个收藏夹共 1327 条，其中正常 1188 条、失效 139 条 → 回填约 1188 张。
  **必须使用带尺寸参数的缩略地址**：Phase 2 实测原图 71.5 KB，若照原图抓取仅封面就占约 85 MB；改用缩略参数（约 15 KB）约 18 MB。
- **增量补齐**：每次收藏夹同步后，对新增或缺 `coverAssetId` 的记录抓取。
- **必须跳过 `attr !== 0` 的失效条目**：它们的封面已是统一占位图，抓下来只会存 139 张一模一样的图，纯占空间且无信息量。同理跳过已注销 UP 主的头像（已是 `noface.jpg`）。
- 使用带尺寸参数的缩略地址（约 15KB/张）。
- 页面渲染优先用归档 Blob，回退 `cover` URL。

**范围与存储**：

- 归档范围：头像（关注模块）+ 收藏视频封面。**历史记录封面不归档**（上万条，量级过大）。
- 图片字节**只存本地 IndexedDB，不进 WebDAV / 本地目录备份**，避免云同步被几十到几百 MB 拖垮。备份只保留元数据与 URL。
- 扩展已有 `unlimitedStorage` 权限，本地容量不是约束。

**重要定位**：由于失效内容一律变占位图，归档**不是"恢复过去"，而是"保护现在"**。已经失效的 139 条真实封面永久不可得；能保住的只有当前仍正常的 1188 条，以及从今往后新增的内容。这决定了实现优先级：**先做增量抓取（新数据不再丢），再做一次性回填（抢救存量）**。

### 8. 与关注模块共享的基础设施

**DB 版本只升一次**（`version: 8` → 9），一次性创建全部新 store：

| store | 归属模块 | keyPath |
| --- | --- | --- |
| `following` | 关注追踪 | `mid` |
| `followingEvents` | 关注追踪 | `event_id` |
| `assets` | 共享 | `id` |
| `vanishedFavResources` | 内容保全 | `[folder_id, id]` |

`assets` 结构（两个模块共用）：

```ts
interface AssetRecord {
  id: string;
  kind: "avatar" | "cover";
  mimeType: string;
  blob: Blob;
  sourceUrl: string;
  createdAt: number;
}
```

迁移时必须同时补 `onupgradeneeded` 分支与 `utils/db.ts` 文件底部那段 `if (!db.objectStoreNames.contains(...))` 兜底块（CLAUDE.md 特别点名了这个坑）。

## 失效内容恢复（Phase 4 实现）

留档只解决"证据不被自己抹掉"。**把已经丢失的标题与封面找回来**是另一半，靠第三方档案。

### 数据源可用性（Phase 4 实测）

| 来源 | 状态 | 实测结果 |
| --- | --- | --- |
| biliplus `/api/aidinfo?aid=1,2,3` | ✅ 可用 | HTTP 200，单条约 1 秒，**批量 3 条约 212ms**。支持一次查多个 aid |
| biliplus `/api/view?id=` | ✅ 可用 | 额外提供 `description`（完整简介）、`typename`（分区）、统计数；`lastupdate` 为当天，服务活跃 |
| jijidown `/api/v1/video/get_info` | ✅ 可用 | 约 800ms–1.1s/条，**仅支持单条**，作为降级来源 |
| xbeibeix | ❌ **已下线** | 20 秒超时，不可用，已从来源列表中移除 |
| B站 `x/web-interface/view` | ❌ 对失效稿件无用 | 返回 `-404 啥都木有`，**不能**用来恢复 |

### 决定性验证：第三方确实持有独立档案

用**真实的**失效稿件（`avid 116704059399752`，`BV1RLEp6KEKi`，`attr 1`）实测：

| 来源 | 结果 |
| --- | --- |
| B站 `x/web-interface/view?bvid=` | ❌ `-404 啥都木有` |
| **biliplus `/api/aidinfo`** | ✅ `私自乱吃激素误入歧途的男娘` + 真实封面 + UP 名 |
| **biliplus `/api/view`** | ✅ 同上，另含简介「男娘」、分区「搞笑」、播放/投币/回复数 |
| **jijidown** | ✅ `私自乱吃激素误入歧途的男娘` + 封面 + `upid` |

结论：**B站 查不到的稿件，biliplus 与 jijidown 能查到**，恢复方向成立。

> ⚠️ **一段被推翻的结论（保留以警示）**
>
> 早先曾用 **av1000 / av5000**（2009 年的远古稿件）当"已删除"样本，得出
> 「`attr 1` 的条目第三方也查不到，只有 `attr 9` 有戏」，并据此：
>
> 1. 写进了本文档
> 2. 在 `utils/favRecovery.ts` 里实现了按 `invalidatedKind` 排优先级
> 3. 把「只能救 UP 主自己删除那一类」写进了给用户的说明
>
> **这个结论是错的，错在取样。** 远古未索引稿件与近期被删稿件完全不是一回事。
> 用用户提供的真实 `attr 1` 样本复测后，biliplus / jijidown 都能恢复。
> 因此代码里的优先级已删除，本文档的边界说明也已修正。
>
> 教训：**验证数据源能力时，样本必须来自真实使用场景**，不能用随手挑的极端值代替。

### biliplus 的 `author` 可能是快照值

同一个 `mid 247177563`，B站 侧显示「俺是帮帮龙」，biliplus 侧显示「忧郁的程序员小鹿」。统计数也不一致（B站 侧播放 218 万，biliplus 侧 18 万）。

因此 `author` **只在本地 UP 名为空或"账号已注销"时**才采用，不做无条件覆盖。我们只取 `title` / `pic` / `author` 三个字段，统计数一律不采用。

### 批量接口的混合命中行为

一批里既有能查到、又有查不到的 aid 时，biliplus 返回 **`code 0` 且只省略缺失项**（实测请求 4 条返回 2 条）。因此可以安全地按批处理，缺失项直接当作"无数据"，不需要逐条重试。

### 三个实现要点

1. **只在确实更优时才覆盖。** 本地可能已经在失效前保住了真实元数据（`saveFavResources` 的失效保护），无脑覆盖会把好数据换成占位内容。判定见 `isBetterTitle` / `isBetterCover` / `isBetterUpperName`。
2. **恢复结果写入 `title` / `cover` 本身，而不是新增平行字段。** 这样收藏夹页、搜索、卡片全部自动生效，无需改动既有 UI。**恢复后的内容直接出现在「收藏夹」页，不在「消失档案」页**——后者只存"整条从在线列表消失"的记录，两者是不同的功能。
3. **必须配套修改 `saveFavResources` 的保护条件。** 原判定是 `!isInvalidatedResource(oldData)`，对恢复过的条目仍然为真（因为 `attr` 没变），会导致**下一次同步把恢复成果覆盖回"已失效视频"**。现在走 `shouldPreserveLocalMetadata`，它额外识别 `recoveredAt`。

### 能力边界（必须告知用户）

- 只针对**失效**条目（`attr !== 0`）且标题或封面仍是占位内容的；本地已有真实数据的不重复查询
- 依赖第三方站点，随时可能下线（xbeibeix 就是先例），因此**只能手动触发**，不放进自动同步
- 部分条目第三方仍无档案（远古稿件等），恢复数可能少于查询数

### biliplus 的返回码语义（一次误判换来的教训）

| 返回 | 含义 | 正确处理 |
| --- | --- | --- |
| `code 0` | 正常，`data` 只含命中的 aid | 直接用 |
| `code -404` `cid无记录` | **本批全部没有记录** —— 正常结果，**不是错误** | 当作 0 命中，继续下一批 |
| `code -503` `停一下！旁友！` | **限流**，等待 30–45 秒即恢复 | **退避后重试同一批**，不能丢弃 |
| 网络 / 超时 / 非 JSON | 环境问题 | 少量重试后交给降级来源 |

**批量大小不是问题。** 实测 20 条一批完全正常，`1 命中 + 19 无记录` 也返回 `code 0`。
`code -404` 只在**整批都无记录**时出现。

> ⚠️ **一次误判的记录**
>
> 真实数据里出现过 `biliplus 批次失败（20 条）：cid无记录`，随后连续失败并触发熔断，
> 整轮 `recovered: 0`。当时把 `-404` 与 `-503` 都当成"失败"，据此做了两个错误处理：
>
> 1. 连续 3 批失败就熔断 → 前几批恰好都是"全部无记录"的正常结果，直接被熔断掉
> 2. 实现"二分降级"（拆小批次直到定位坏 aid）→ **方向完全错了**，批次大小本来没问题，
>    二分只会让限流更严重
>
> 修正后：`-404` 当正常结果、`-503` 退避重试、**移除二分**、批间间隔从 800ms 提到 3 秒。
> `classifyBiliplusResponse` 有专门的单测锁住这套语义。
>
> 教训：**看到错误码先确认语义，别急着设计容错机制**。容错机制本身也会成为 bug 来源。

限流阈值很低（连续约 3–6 次请求即触发 `-503`），所以批间必须留足间隔。

### 一级来源（分P标题）为什么在真实数据上是 0 —— 需要换接口

实测诊断输出（真实运行）：

```
样本记录诊断：aid=13452520 page=1 pages=无
样本记录实际字段：id, type, title, cover, intro, page, duration, upper, attr,
                 cnt_info, link, ctime, pubtime, fav_time, bv_id, bvid,
                 season, ogv, ugc, media_list_link, folder_id, index
```

**`page` 在，`pages` 不在。** 即我们用的**鉴权接口** `x/v3/fav/resource/list`
不返回分P 数组；只有**非鉴权接口** `medialist/gateway/base/spaceDetail` 才返回。

这正对应社区脚本自己的提示："建议将收藏夹设为公开，可以通过 B站官方非鉴权API
查询并恢复更多视频信息**和分P**"。

所以分P标题还原要真正生效，**必须额外调用公开接口**。代价：公开接口的 `ps` 上限为 20，
814 条内容的收藏夹需要约 41 次请求，且 B站 侧同样有限流——因此它是可选的一轮，
放在 biliplus / jijidown 之后，只对仍未恢复的条目所在收藏夹触发。

> 教训：上游用了 `...media` 展开保存，让我误以为"接口返回的一切都在库里"。
> **实际字段清单才是唯一证据**——诊断日志打出的 `Object.keys()` 一次就定位了问题，
> 比反复猜测省事得多。

### jijidown 也会限流，而且表现和"查不到"极像（第二个误判）

社区脚本的真实判断逻辑：

```js
} else if (json.code == 0 || json.upid == undefined) {   // 大概率是请求过快
    setTitleRetry(...)   // 提示"请求过快，请点击手动加载"
} else if (json.upid == -1 || json.upid == 0 || json.title == "视频去哪了呢？" ...) {
    // 确实查不到
```

| 表现 | 含义 |
| --- | --- |
| `upid` 是合法正数 | 命中 |
| **`upid` 缺失 / `code === 0` / HTTP 502、503** | **限流** —— 必须退避重试 |
| `upid === -1` 或 `0`、占位标题 | 确实没有这条记录 |

早先的实现把 `upid` 缺失直接当成"没有数据"丢弃，**把限流误判成查无此片**。
真实数据里 71 条只恢复 25 条，剩下的 46 条大多就是这么被扔掉的——
用户对照社区脚本的观察（"基本全都修复了，只是需要手动重新加载"）直接指出了这一点。

**改进**：不再靠人工点击重试，而是自动多轮——本轮被限流的条目退避 15s / 30s 后整批再跑，
最多 3 轮。超过 3 轮仍被限流的会明确告知"稍后再点一次可继续"，而不是静默算作查不到。

> 这两个误判（biliplus 的 `-404`、jijidown 的 `upid` 缺失）是同一个毛病：
> **把"限流/无记录"这类正常响应当成了故障或反例**。第三方接口的语义必须逐个确认，
> 不能凭直觉归类。

### 实测覆盖率（真实数据，71 条待恢复）

| 来源 | 命中 | 说明 |
| --- | --- | --- |
| 分P标题（本地） | 0/71 | `pages` 未存储；需走公开接口，见上 |
| biliplus | **0/71** | 4 批全部返回正常 `-404`，即该用户这批内容 biliplus 确实没有 |
| jijidown | **25/71** | 修正限流误判前的结果；剩余 46 条多为限流被误判 |

结论：**jijidown 是这套数据的主力来源**，不能只依赖 biliplus。
biliplus 仍保留在流程里——批量查询成本低（4 次请求覆盖 71 条），
作为廉价的前置尝试是合理的，只是不能假设它一定有货。

### 恢复流程（按成本从低到高，共五级）

| 级别 | 来源 | 覆盖 | 成本 | 实测 |
| --- | --- | --- | --- | --- |
| 0 | **本地交叉引用**（观看历史 / 喜欢的音乐 / 订阅合集） | 封面 | **零请求** | 待验 |
| 1 | B站 分P 标题推测（`pages[0].title`） | 标题 | **零请求**（需先有 `pages`） | 0/71（`pages` 需公开接口补） |
| 2 | biliplus `/api/aidinfo` 批量 20 条/批 | 标题、封面、UP 名 | 每 20 条一次 | **0/71** |
| 3 | **B站 非鉴权公开收藏夹接口** | `pages`、标题、封面 | 每页一次（用 index 定位，29 页覆盖 46 条） | **41/46** |
| 4 | jijidown 单条 + 自动多轮重试 | 标题、封面、UP 名 | 每条一次 | 25/71 |

**第 0 级（本地交叉引用）** 的思路：同一个稿件可能同时存在于观看历史、喜欢的音乐、
订阅合集里——这些记录是稿件失效**之前**抓的，封面往往还是好的，而且都带 `bvid`
可以直接匹配。**零请求**，所以必须排在最前。

**第 3 级是覆盖面最大的一级**（实测 41/46）。关键在于用记录的 `index` 直接算出候选落在
公开接口的第几页，把 814 条收藏夹的 41 次翻页降到 29 次，且只请求包含候选的页。

> **流水线必须共用一份工作副本。**
> 第 0 级补好的封面，若后续级别拿着**旧对象**去改标题，最后统一写库时会把刚补上的封面
> 又覆盖回占位图。实现上用 `Map<id, FavoriteResource>` 贯穿全程，各步都从它读取、写回它，
> 最后一次性落库。

### 封面恢复的四种途径（回答"封面还有别的方案吗"）

1. **B站 公开收藏夹接口** —— 标题与封面一起回来，实测主力
2. **本地交叉引用** —— 历史记录 / 喜欢的音乐 / 订阅合集，零请求
3. **biliplus `/api/view` 的 `v2_app_api.first_frame`** —— 视频首帧当封面兜底（该接口对我们这批数据 0 命中，但值得保留在候选里）
4. **封面字节归档** —— 唯一"防患于未然"的方案：在封面还正常时把字节存下来。
   `utils/assetArchive.ts` 已就绪，但 `favResources` 的封面回填任务**尚未接入**（见集成点清单）。
   前三种是"事后找回"，只有这一种能真正保证不丢。

### 实测覆盖率（真实数据，71 条待恢复 → 两轮后剩 5 条）

| 轮次 | 来源 | 命中 |
| --- | --- | --- |
| 第 1 轮 | jijidown | 25 |
| 第 2 轮 | B站 公开收藏夹接口 | 41 |
| 合计 | | **66/71（93%）**，剩余 5 条 |

biliplus 两轮均为 **0 命中**（4 批 + 2 批全部正常 `-404`）——对该用户这批内容它确实没有。
**保留它是因为批量成本低**（4 次请求覆盖 71 条），作为廉价前置尝试合理，但不能假设它有货。

### 三级恢复流程（按成本从低到高）

恢复不是"只查 biliplus"，而是三级递进——**能本地解决的就不要麻烦外部站点**：

| 级别 | 来源 | 覆盖字段 | 成本 |
| --- | --- | --- | --- |
| 1 | **B站 分P 标题推测**（`pages[0].title`） | 标题 | **零请求**，数据本来就在收藏夹接口返回里 |
| 2 | biliplus `/api/aidinfo`（批量 20 条/次） | 标题、封面、UP 名 | 每 20 条一次请求 |
| 3 | jijidown `/api/v1/video/get_info`（单条） | 标题、封面、UP 名 | 每条一次请求，仅对前两级都失败的条目发起 |

**第 1 级是覆盖面提升的关键。** B站 把失效稿件的 `title` 换成「已失效视频」，但
`pages[0].title`（第一P 标题）往往还在。稿件只有一个分P 时该分P标题即稿件标题，
可直接还原。策略来自社区脚本的实测经验，还原结果追加 `（视频投稿上传时的标题）`
后缀以标明是**推测**而非官方标题。

多分P 的稿件不采用该策略——那时第一P 标题是子标题，还原出来的是错的（有负例单测锁定）。

> 上游从未声明也从未使用 `pages` 字段。它一直在接口返回里，只是被 `...media` 展开
> 存进了库却没人读——**"数据早就有，只是没用"是这类功能最常见的浪费**。

### 一个必须避免的判定错误：`needsRecovery` 不能用 `recoveredAt` 提前返回

分P标题还原**只能补标题**，封面还得靠第三方。如果 `needsRecovery` 写成
"`recoveredAt` 有值就不必再恢复"，那些只补了标题的条目会**永远失去补封面的机会**。

正确判据是**"现在缺什么"**，而不是"有没有补过"：

```ts
return isPlaceholderTitle(resource.title) || isPlaceholderImage(resource.cover);
```

好处是它天然收敛：标题与封面都真实后自然返回 `false`，不会无限重复查询。
